# ADR-004：Nimbalyst 三栏入口、任务适配层与无密钥原型

状态：设计采用，待实施验证。日期：2026-09-14。

v2.3 更新：[ADR-005](ADR-005.md) 将 M0 扩展为共享核心的 GUI/TUI/CLI/Hooks。下文保留原始取舍语境；当前实施按 ADR-005 和主 SPEC，不能仅交付 GUI。

## 背景

用户选择 UI v2：左侧集中设备和管理入口，中央简洁看板，右侧选中任务会话。Cursor 独立演示已验证搜索、新建与模拟卡片动作，但它不是 Nimbalyst 的实现。当前 Nimbalyst 已有 Tracker 看板及会话布局，应复用而不是启动第二套主应用。

## 决策

1. 采用三栏布局和 TODO/RUNNING/DONE/ARCHIVED 展示；设备与运维指标不占中央。
2. 在 Nimbalyst 的现有渲染/宿主边界上实现 Babel 工作台；不嵌入 Cursor Next.js 页面作为最终产品。
3. 复用上游已有 TrackerDataSource，原工作区保持 ElectronTrackerDataSource，共享工作区使用拟新增 BabelTrackerDataSource，模拟使用 DemoTrackerDataSource。原生 Trackers 与 Babel 是同一条目的两个视图，ID 与数据源一致；所有写入口通过统一命令路由，执行另外接 RunControlClient。
4. Ubuntu 单实例任务后台初期使用本地 SQLite 事务库，通过 API 提供共享访问；不共享客户端 PGLite 或 SQLite 文件。
5. 先交付 Nimbalyst 内无 Key、隔离 profile 的 M0；生产任务状态由后端验证事件与人工审查控制，不复用演示的任意状态推进接口。

## 取舍

直接只传 KanbanBoard.overrideItems 虽能显示共享卡片，但内部保存路径仍指向原 Tracker，容易污染本地数据。因此先封装写入命令，必要时抽出纯展示组件，接受少量宿主改动。

直接复制 Cursor 页面能更快展示，但会产生两套主题、会话、任务数据库与快捷键，无法兑现 Nimbalyst 单一工作台。只借鉴其搜索、新建和卡片动作。

SQLite 适合首期单台 Ubuntu 后台，简化维护；多实例服务必须另行设计并迁移，不能直接共享文件扩容。

补充依据：[Trackers 一一映射源码审计](../NIMBALYST-TRACKER-MAPPING.md) 已核实上述上游接口，并明确 Ready、Releases、approved、归档及 Launch Session 的不同语义。

## 后果与验收

增加宿主适配、后台和 Worker 工作量，同时保留 Nimbalyst 的文档/会话能力。NB-00 核验包许可与构建边界；NB-01 同步迁移旧合同；UI-01 至 REG-01 的验收标准见 [开发 SPEC](../NIMBALYST-DEVELOPMENT-SPEC.md)。本决策细化 ADR-003，不恢复 Nextcloud Talk/Deck 为必选底座。
