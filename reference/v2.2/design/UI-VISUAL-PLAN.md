# Nimbalyst UI 视觉覆盖与验证计划

版本：候选 v1，2026-09-14。本轮只准备计划与提示词，没有新增效果图，也没有批准最终 UI。

共同约束：[视觉合同](visual-contract.md)、[开发 SPEC](../NIMBALYST-DEVELOPMENT-SPEC.md)、[Trackers 映射](../NIMBALYST-TRACKER-MAPPING.md)。现有 [v2 图](babel-dashboard-v2.png) 是方向稿。

## 1. 结论与最小范围

需要补关键视图，避免开发 Agent 只凭一张运行画面猜测新建、验收、历史及原生类型入口。建议五张主图加三类交互／变体验证。每个状态都画整页既不能证明交互，又会增加不同图之间的冲突。

本轮不自动批量生图。后续按 V01 → V03 → V02 → V04 → V05 顺序逐张形成候选，先核对共用母版再继续。实现出共享组件后优先用真实截图补齐变体。

## 2. 八个覆盖场景

| 编号／优先级 | 场景与固定焦点 | 交付方式 | 关键判定 |
|---|---|---|---|
| V01／P0 | 首页，Trackers 的视图／类型展开，右栏关闭 | 独立候选图；之后真实页面截图 | Ready、类型、显示入口可发现；中央保持四列；无任务被自动启动 |
| V02／P0 | 选中 TODO：说明、依赖、验收和启动摘要 | 独立候选图；新建／校验／保存用交互 fixture | 原生 TrackerItemDetail 数据完整；保存、保存并启动、启动前核验清楚 |
| V03／P0 | 选中“接入任务同步”：当前 run 会话 | 修订 v2 成为运行母版 | 左栏映射补齐；运行／完成／归档列无新建；消息、工具、补充输入清楚 |
| V04／P0 | 当前执行待人工审查，查看差异和验收证据 | 独立候选图 | 不将退出进程或 approved 当 DONE；接受与要求修改有明确语义 |
| V05／P0 | 归档任务的执行历史；查看旧 run | 独立候选图 | 归档与完成分开；恢复不会执行；不同 run 与人工讨论不混淆 |
| X01／P0 | 同一记录在原 Trackers 与执行视图之间切换 | 可交互 fixture＋实现后的成对截图／录像 | ID、类型、字段、revision 一致；原生 Releases 不能变为归档 |
| X02／P1 | 等待输入、失败、失联、取消待确认、版本冲突、空状态、加载态 | 可注入状态的 fixture；必要时一张组件状态图 | 错误文字和可用动作正确；失联不允许盲目重试；拒绝命令不伪装成功 |
| X03／P1 | 深色、窄窗口、移动、字体放大、键盘焦点 | 同一组件的渲染截图；结构不明时补一张窄屏稿 | 遵守 SPEC 断点与宿主 token；没有另一套独立样式或不可达动作 |

五张主图使用同一套组件设计与 fixture 定义。V03、V04 可以是同一任务的不同时间快照；V05 可选既有归档记录。图间的时间变化必须在场景注释里声明，而不是悄悄修改标题和编号。

## 3. 每个主图需要表达的最少信息

### V01：看板首页

- 复用宿主框架，Trackers 模式对应工作区的任务看板；左边明确显示“视图／类型”。允许折叠其他左侧分组，不能把侧栏新增内容塞成另一块中央面板。
- 默认显示可执行类型的四列；“All／全部类型”是可进入的原生视图，不表示所有类型都能自动运行。
- 保留显示模式、保存视图和过滤的轻量入口；一个全局搜索，不重复画两个同用途输入框。
- 五张初始卡片，右栏关闭时中央扩展。新建只出现在允许的位置。

### V02：待办和启动

- 默认选中“PDF 行间对译”。来源是任务出处，正文与依赖仍归原生 Tracker。
- 任务标题和正文可编辑；验收项、上下文、目标设备及 provider 展示于任务详情／启动摘要，不常驻中央。
- 显示保存与开始模拟的区分；完整启动表单、字段错误、断网和版本冲突通过 fixture 验证，不要求全部塞进一张图。

### V03：运行会话

- 在 v2 的密度和三栏结构上修正视觉合同 VC-01 至 VC-08；不重新设计品牌与配色。
- 右侧设备名是当前 run 的只读元数据，不是可以更改正在执行设备的下拉框。
- 工具输出按需展开，保持稀疏中央。消息列表与输入草稿在切标签时保留。

### V04：差异和验收

- 选中任务仍在运行列的待审状态；右栏显示当前 run 的基线、文件差异与必需验收项，细节按需展开。
- “接受结果”在政策允许时才可用；“要求修改”进入明确的新执行路径，不能把普通聊天发送当重试。
- 验证失败、豁免、证据未到齐属于 X02 状态，不为了画面整齐伪造全绿。

### V05：历史和归档

- 选中归档列中“工作台布局初稿”，保持相同 Tracker 身份。明确显示归档、归档前结果和恢复入口。
- 右栏按 run 展开历史，当前查看哪次执行清楚；人工评论与 Agent 执行事件区分。
- 恢复返回原语义状态；查看旧 run 不改变当前执行、不新建会话。原生 Release 记录不放入该列做示例。

## 4. 交互优先于生图的项目

X01 使用同一 provider／atoms／命令入口完成双向修改；对照证据包含 `(projectId, trackerId)` 与 revision。成对截图应来自同一次真实演示操作，不能用两张生成图当成一致性测试。

X02 至少覆盖：requested 接收前仍待办、accepted 后运行、等待回答绑定请求、验证失败不可完成、取消未确认不可重试、失联待核对、409 保存冲突、归档恢复、只读来源限制、长标题、搜索无结果。拖拽、键盘等价操作、返回焦点与新消息不抢滚动都需实际操作。

X03 继承 SPEC 的 1586×992 主视口及 1280、1024、768、390 CSS px 检查点，并检查 200% 字体；按 ≥1536、1100–1535、768–1099、<768 的策略适配。深色从同一语义 token 切换。主视图图片的分辨率不是响应式功能证明。

## 5. 产物命名与生成纪律

后续可采用 `V01-board-overview-candidate` 等场景名；本轮只定义逻辑名，文件未生成。每份产物旁记录：场景、fixture 版本、主题、视口、选择的 tracker／run、所依据的规格版本、生成工具或实现提交。

没有文件就不要创建“已完成”链接。不得在每张图里独立发明数字、任务数据、在线设备、验收结果或完成策略。先修正母版，再复用同一参考图生成后续状态；完成后核对文字、入口、数量、类型与按钮语义。

## 6. 何时能成为基准

1. 候选符合 Trackers 映射与视觉合同，未保留 v2 的八项冲突。
2. 用户已经审阅需要确认的主布局／关键动作，并明确接受该版本；未得到反馈不写“最终批准”。
3. 把接受范围与未决定事项记录下来。截图只批准视觉方向时，不外推为全部状态机或信息模型批准。
4. 用原生组件实现后捕获同 fixture 的截图，执行 SPEC 的 UI／双面板验收；原型、模拟、真实 Worker 分别标记。

M0 的交付应是可启动、可操作的 Nimbalyst 页面、共享 fixture、必要截图及操作记录。效果图系列为这个目标服务，不替代它。
