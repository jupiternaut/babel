# Nimbalyst GUI 主视图候选图：后续逐张生成提示词

版本：候选 v2，2026-09-14。对齐 v2.3；此文件只准备 GUI 生图提示词和 TUI 捕获说明，本轮没有执行图像生成或终端验收。

先读 [视觉合同](visual-contract.md)、[场景覆盖计划](UI-VISUAL-PLAN.md)、[Trackers 映射](../NIMBALYST-TRACKER-MAPPING.md) 与 [TUI/CLI 与 Hooks 契约](../NIMBALYST-TUI-HOOKS-SPEC.md)。现有 [v2 图](babel-dashboard-v2.png) 仅作为 GUI 方向参考，不是已批准最终图。

## 使用方式

一次只执行一个场景。先查看所引用图像，再以当前母版作编辑参考；不要分别从零生成五套风格。V01 先解决左栏映射和首页，V03 随后锁定与 v2 一致的三栏运行构图，再生成 V02、V04、V05。

统一场景数据见 [demo-fixtures.json](demo-fixtures.json)：V01–V05 与对应 fixtureId 一一登记，V04 是同一运行记录的待审快照。调用后记录真实文件尺寸，不把提示词中的尺寸当输出元数据。图像生成不能保证中文、数字或尺寸完全准确；逐张核查，后续以真实组件截图建立可重复基准。

任何候选图片都有小而清楚的“设计稿 · 演示数据”标识，不能显示成已连上用户设备或账号。不要用真实用户文件、密钥、账号、主机凭据或会话内容。

V01–V05 五张 GUI 图继续保留。它们不覆盖独立 TUI，也不证明三端业务对等；TUI 不套用下方 CSS 尺寸、圆角和桌面三栏母版，按视觉合同的字符网格与操作基准捕获真实实现。

## 所有场景共用母提示词

```text
生成 Nimbalyst 中“巴别塔 BABEL 执行视图”的单张桌面 UI 候选图。参考当前附图的克制浅色、简体中文、紧凑工具栏和留白；它是实际生产力应用的设计稿，不是营销展示页。保留 Nimbalyst 的原生应用框架和可复用控件，不做另一套独立产品外壳。不要人物、字幕、壁纸、装饰性监控卡、发光、玻璃或大渐变。

用户要求：复杂导航都在左侧；中央一定简洁；任务卡只留标题和必要状态；选中任务后右侧渐进显示内容。原生 Trackers 与执行看板是同一条目的两种布局，不生成第二套 Task；类型、保存视图和生命周期是独立维度。

左栏：工作区入口中有任务看板、Agent 会话、项目文件、项目讨论、知识与 PDF。任务看板下保留可折叠 Trackers 分组，内部为“视图”和“类型”：视图有 Ready；类型包含全部、计划、决策、缺陷、任务、想法、里程碑、发布，也能容纳自定义类型。设备、项目、集成、运维在左栏其他组。可折叠次要组并有清楚的滚动区域，不要把所有组强行压小塞满屏幕。使用一个明确的宿主全局搜索；不要在左栏重复另一个同用途搜索。

中央：只有轻量工具栏、四列和少量卡片。四列固定为待办、运行、完成、归档；运行/完成/归档列头没有新建加号。保留必要的显示/筛选轻量菜单，原生模式和保存视图应可发现，不要加第二排大工具栏。新建动作在当前执行总览叫“新任务”；原生发布类型中的新建语义应为“新发布”，不要把发布映射成归档。

使用同一套图标、字体、分隔与颜色。参考现有宿主 --nim-* 语义色，浅色画布、清晰主文字、安静次文字、细线和克制选择色；不能在提示词中假称已核验某个具体 token 名。参考视口 1586×992，三栏出现时左约240、右约390、中央约956 CSS px；具体由画面布局协调，不压扁卡片。正文约14px、辅助约12px，4/8px间距，1px分隔，4–8px圆角。标题最多两行、辅助最多一行、卡片常规64–88px；不硬裁长文字。状态有文字，不能只靠颜色。

使用下面场景指定的同一组演示任务和时间快照。不得随机增加任务、运行次数或数量。仅画这一个场景，不拼成海报，不额外创造控件。底角标注“设计稿 · 演示数据”。
```

## V01：看板首页与 Trackers 映射

建议参考：现有 v2 方向图；用户提供的原生 Trackers 截图用于确认入口语义。输出候选后先核对左栏，再进行其他状态。

```text
在共用母提示词基础上生成 V01。

此图没有选中任务，右侧详情关闭，中央使用腾出的宽度；不要保留一个空白右栏。左侧当前位于任务看板，展开 Trackers 的视图/类型，能看见 Ready、全部、计划、决策、缺陷、任务、想法、里程碑、发布；集成和运维可折叠，设备组保持简短。

演示初始画面正好五张卡：待办“PDF 行间对译”“整理研究资料”；运行“接入任务同步”，辅助“Pi · 运行中”；完成“统一任务状态”；归档“工作台布局初稿”。列数为2、1、1、1。第一张待办只有安静的 Google Tasks 来源提示。归档卡不命名为发布或 Release。

卡片靠近列顶，剩余中央保持留白。设备选择与刷新全部留左侧，没有中央指标。只保留顶层新任务和待办列可用的新建；其他列只必要省略菜单。工具栏能轻量发现原生显示模式和保存当前视图。
```

## V03：当前执行会话母版

建议参考：经映射检查的 V01 母版＋现有 v2 的三栏会话布局。未有已核对 V01 时仍只作候选，不写 accepted。

```text
在共用母提示词基础上编辑为 V03，保持左栏、字体、图标、间距和同一批五张任务完全一致，不重新设计配色。

选择运行卡“接入任务同步”，用细选择边框，不改变卡片大小。右侧打开，标题为接入任务同步，下方只读元数据“Pi · Ubuntu · 第2次执行”。标签为会话、差异、历史，当前会话。

会话内只有一条简短助手消息“已完成任务映射，正在处理增量同步。”和三个工具活动：读取 Google Tasks、按任务 ID 去重、处理分页与断线重试。前两项完成，最后一项执行中。它们是演示活动，不表示整张任务已完成。下方安静一行“正在编辑 google-tasks.ts…”。右栏其余留白，底部补充输入和发送，附近可有小型文件差异摘要。

不放完整日志、终端、执行历史卡、设备指标或长路径。设备是当前执行的只读说明，不画成可更改运行设备的下拉框。保持列头2、1、1、1；所有模拟在线或同步内容受统一演示标识覆盖。
```

## V02：待办详情与启动摘要

建议参考：V03 的同一三栏母版，切换选择状态与右栏内容；不要为新建表单另创视觉系统。

```text
在共用母提示词基础上编辑为 V02。左栏和五张任务位置沿用母版；取消运行卡的选择，选中待办“PDF 行间对译”，右栏标题相同。

右栏是原生 Tracker 任务详情，不是聊天。显示简短任务说明、Google Tasks 来源、小型依赖/上下文入口、两条清楚可判定的演示验收要求。任务仍为待办，不因为打开详情变为运行；右侧没有正在输入的 Agent 消息。

右栏底部提供保存与开始模拟的明确区分。启动摘要可以显示目标设备、provider、代码基线及将使用的任务版本，但保持紧凑，仅在右侧展示；不把它们复制到中央卡片或设备大面板。正文、上下文、验收不压成一句 prompt。

缺失信息的错误态和完整新建模态框不塞进此图；它们由之后的交互 fixture 验证。不要画一个点击即偷偷创建第二条同名任务的动作，不显示真实 API Key 输入要求。
```

## V04：差异、验证与人工验收

建议参考：V03。此图是“接入任务同步”的后续待审快照，任务身份不变；不得将此阶段画为 DONE。

```text
在共用母提示词基础上编辑为 V04，沿用三栏与左侧导航，选择“接入任务同步”，它仍在运行列，辅助文字为“Pi · 待验收”。五张主任务不增加副本，列数保持2、1、1、1。

右栏顶部仍是同一任务、Ubuntu与第2次执行；切到差异标签。用 Nimbalyst 风格展示绑定该 run 的简短基线说明、2个演示变更文件和可折叠的小段差异，旁有增删统计但不占据大色块。

右栏呈现验收证据入口和两条必需验收项的状态；本场景采用演示证据已满足但尚未人工接受的状态。底部动作是“接受结果”和“要求修改”。只有接受才可使任务进入完成；不要显示任务已成功完成的总横幅，不把 approved 写成 done。

保持渐进披露和留白，不同时展开全部文件、日志、终端、历史与讨论。真实基线、路径和结果均由演示 fixture 给出，图中不要伪造用户仓库的真实提交。
```

## V05：归档、旧 run 与恢复

建议参考：V03。使用固定归档记录，不把正在执行的任务强行塞入归档。

```text
在共用母提示词基础上编辑为 V05，沿用三栏母版。选择归档列“工作台布局初稿”，其他卡片保持原位，不新增同名任务；四列计数仍是2、1、1、1。

右栏显示相同任务标题和明确归档标识，当前是历史标签。以简洁分组表示任务活动与执行历史；run记录包括执行次数、时间、设备与结果，当前展开一个旧run，标明只读。原生人工讨论与 Agent 执行记录分开。

右栏提供“恢复”动作，并以短说明表达“恢复到归档前状态，不自动执行”。不要把恢复叫开始，不提供会自动发起新run的普通发送框。历史中不凭空捏造多次执行；若统一fixture只有一条run则只显示一条，其余以折叠任务活动表达。

Releases属于原生发布类型，在左栏仍独立存在；此归档画面不能以发布版本列表替代，也不能把归档表示为删除。
```

## 不应作为五张独立生成图补齐的内容

- X01 双面板同 ID：用真实 demo 在原生／新布局之间切换并截图，生成图片不能证明同一数据源。
- X02 异常与微交互：用共享组件和注入状态验证。必要时制作组件状态图，但不重新设计整页。
- X03 深色与响应式：优先从相同组件切 token／视口得到截图。只有结构未确定时才基于母版补窄屏候选图。

## TUI 使用实际捕获流程，不使用生图提示词验收

M0 必须运行独立 TUI，并按 [覆盖计划的 TV01–TV05](UI-VISUAL-PLAN.md#5-tui-实现截图与操作基准) 捕获首页、编辑/启动、会话、差异/验收、历史/恢复。用同一隔离 demo 服务执行三端交叉操作；保留中文宽字符与输入法、键盘、鼠标、resize、重连和退出恢复的实际记录。

每份 TUI 截图附 120×40、80×24 或 160×48 的实际列×行、终端与系统版本、fixture、实现提交和选择的记录/run。PTY/ConPTY 测试提供输入与状态断言，Hooks 测试另附命令结果、关联事件和查询结果。AI 生图即使外观像终端，也只能标设计参考，不能替代 TUI 截图、PTY 验证或计为 M0 通过。

未来用户明确要求生成时执行对应场景；生成之后应核查实际输出与共同合同，不因图片视觉好看跳过数据和操作语义检查。
